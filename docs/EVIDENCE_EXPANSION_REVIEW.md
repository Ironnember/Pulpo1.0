# Evidence Expansion Review v0

## Purpose

Evidence Expansion Review is a read-only Intelligence/Assurance procedure for connecting new evidence to the wider Pulpo proof path without creating a second authority, policy, memory, router, executor, or ledger.

It broadens analysis. It does not broaden authority.

## Constitutional placement

This procedure sits outside the governance kernel and consequence path.

It may:

- inspect evidence already within authorized informational scope;
- compare new material with canonical and durable evidence;
- identify contradictions, dependencies, blocker classes, and repeated structures;
- generate testable hypotheses and proposed proofs;
- recommend the smallest proof that can falsify or verify a material claim.

It may not:

- mutate canonical Pulpo state;
- issue or consume permits;
- change policy or directives;
- create or widen authority;
- write governed outcome memory directly;
- perform connector writes, deployment, purchases, messaging, credential operations, or other consequential actions;
- treat prediction, retrieval relevance, model confidence, recurrence, or convenience as authority.

Any transition from analysis into consequential execution remains subject to the normal Pulpo lifecycle:

`Purpose -> Intent -> Authority -> Policy -> Decision -> Permit -> Execution -> Evidence -> Reconciliation -> Memory -> Adaptation -> Purpose`

## Review scopes

For each new evidence item, review only the scopes relevant to the current objective:

1. **Artifact** — What does this exact item directly show?
2. **Temporal** — What happened immediately before and after it?
3. **Authority** — What intent, delegation, approval, or permission should have existed?
4. **Capability** — What capability was available, activated, retained, or withheld?
5. **Execution** — What actually ran or changed?
6. **Evidence** — What independently supports or contradicts the result?
7. **Contradiction** — Which current claims, states, or records conflict with this item?
8. **Dependency** — Which systems, credentials, people, providers, or prior states must be true?
9. **Cost/resource** — What money, credits, quota, compute, time, risk, or opportunity was consumed or exposed?
10. **System** — Which model, UI, platform, plugin, provider, workflow, or trust-domain interaction is implicated?
11. **Historical** — Have materially similar conditions appeared before?
12. **External** — Is outside evidence required to verify, compare, or bound the claim?
13. **Proof path** — What evidence is still missing before the claim can become Verified?
14. **Pattern** — Does this item strengthen, weaken, split, or falsify an existing pattern hypothesis?

Broader inspection means broader reasoning across legitimately readable evidence. It does not authorize new connectors or wider data access merely because they might be useful.

## Blocker classes

Use blocker labels to explain why a desired claim cannot yet become Verified:

- **Authority blocker** — legitimate authorization is missing or cannot be established.
- **Custody blocker** — an alternate consequence-capable path remains reachable.
- **Evidence blocker** — execution may have occurred, but independent observation is insufficient.
- **Provenance blocker** — a current state exists, but the transition that produced it is not reconciled.
- **Externality blocker** — simulation or local proof exists, but the real external provider has not been tested.
- **Reproducibility blocker** — build-loop evidence exists, but cold independent reproduction does not.
- **Semantic blocker** — exact technical binding exists, but the object may not represent the intended human meaning.
- **Platform-opacity blocker** — behavior is observable, but the mechanism producing it cannot currently be verified.
- **Economic blocker** — metered-resource or billing consequence cannot be reconciled from authoritative usage evidence.

A blocker label is analysis, not canonical truth. It must not change policy or execution behavior by itself.

## Pattern states

Keep pattern reasoning separate from Pulpo claim classification:

- **Observation** — one directly supported event or state.
- **Pattern hypothesis** — multiple observations suggest a common structure or mechanism.
- **Verified failure mode/invariant** — a controlled proof has reproduced the mechanism or invariant under its stated boundary.

Do not convert recurrence into verification. A predicted pattern remains Inferred until controlled evidence supports it.

## Operating loop

Use this review sequence before selecting a new proof:

`Observe`
-> `Inspect within informational authority`
-> `Establish temporal/system context`
-> `Connect dependencies and related evidence`
-> `Reconcile contradictions`
-> `Classify claims`
-> `Identify blocker class`
-> `Compare with known pattern hypotheses`
-> `Generate a falsifiable prediction`
-> `Select the smallest proof that retires the uncertainty`
-> `Obtain separate authority if consequence is required`
-> `Execute through the existing governed path`
-> `Observe independently`
-> `Reconcile`
-> `Record through existing canonical evidence and memory rules`

## Guardrails

The procedure is subordinate to Pulpo's existing evidence hierarchy and claim classes.

- Executable behavior and current canonical code outrank narrative pattern summaries.
- A contradiction must be surfaced, not silently normalized.
- A new observation may downgrade confidence in a pattern.
- A pattern may recommend a test; it may never authorize one.
- Read-only evidence inspection must not retain or expose canonical writers.
- Persisted analytical artifacts must remain non-authoritative unless separately admitted through existing Pulpo governance.
- No second ledger, memory governor, policy engine, router, or executor may be introduced for this procedure.

## Example structural signatures

These are hypotheses that may guide testing, not automatic truths:

- `AVAILABLE_CAPABILITY != AUTHORIZED_CAPABILITY`
- `OBSERVED_STATE != LEGITIMATE_PROVENANCE`
- `EXECUTOR_SUCCESS != VERIFIED_CONSEQUENCE`
- `ONE_TRUST_DOMAIN_REPORT != INDEPENDENT_REALITY`
- `CONTEXT_RELEVANCE != INTENT != AUTHORITY`

## Output format

A review should produce a compact record containing:

- **Objective**
- **New evidence**
- **Relevant connections**
- **Contradictions**
- **Claim classes**
- **Blocker class(es)**
- **Pattern hypothesis(es)**
- **Falsifiable prediction**
- **Smallest next proof**
- **Authority required for that proof**
- **Remaining unknowns**

The review ends at recommendation unless the next step is already independently authorized.

## Doctrine

**Intelligence proposes. Governance disposes. Execution obeys. Evidence reports.**
