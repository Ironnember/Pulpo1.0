# DM-001: Directive authority continuity

Inspection base: protected `main` at `ca3636680ca50356406519a5722444c0742afb39`.

This proof record organizes an already-present canonical software proof. It does not create runtime authority, add a memory governor, add a policy engine, add a second ledger, execute a provider action, publish a release, or change repository protection.

`authority_effect=none`

## Claim

A directive can authorize consequence only when it exists as authenticated, immutable/versioned, scoped, canonical governance state. Ordinary chat text, retrieval score, model summaries, repeated use, delegated convenience, and executor success cannot create, broaden, revive, or substitute directive authority.

Directive Memory is therefore a governed policy-state projection, not a conversational-memory feature and not a second source of governance truth.

## Existing implementation seam

Runtime:

- `pulpo/directives.py`
- `pulpo/state.py`
- `pulpo/kernel.py`

Tests:

- `tests/test_directives.py`
- `tests/test_directive_parent_activation_race.py`

The implementation uses the existing kernel, policy, approval verifier, permit, state, and audit chain. It deliberately avoids an alternate directive state, alternate clock, alternate policy evaluator, second memory system, or second evidence ledger.

## Invariants covered

### 1. Ordinary chat text cannot create an authoritative directive

Test coverage:

- `test_chat_or_retrieval_cannot_create_authority`

Expected result:

- Projection evaluation over an inactive directive denies with `directive_not_authorized`.
- Retrieval-like relevance or remembered instruction text can inform proposal only; it cannot authorize execution.

### 2. A valid directive identifies an independently authenticated authorizer

Test coverage:

- `test_activation_requires_verified_external_authority`
- `test_untrusted_issuer_is_denied_even_with_valid_approval`

Expected result:

- Invalid approval signature denies activation.
- Trusted approval for an untrusted directive issuer still denies with `directive_issuer_untrusted`.

### 3. Approval binds the exact directive object

Test coverage:

- `test_approval_is_bound_to_exact_directive_digest`

Expected result:

- An approval envelope for one directive digest cannot activate a broadened or substituted directive object.

### 4. A directive constrains but does not replace the kernel

Test coverage:

- `test_authorized_directive_constrains_but_does_not_replace_kernel`

Expected result:

- The directive can narrow the action/resource/budget surface.
- The kernel remains the authority path for permit issuance.

### 5. Retrieval score or model-generated summaries cannot raise authority

Test coverage:

- `test_model_summary_or_retrieval_score_cannot_raise_authority`

Expected result:

- A directive with cost cap 1 still denies an otherwise relevant action at cost 2.
- Retrieval relevance does not modify directive max cost, scope, issuer, or authority.

### 6. Revoked/superseded directives cannot authorize execution after restart

Test coverage:

- `test_revocation_requires_new_authority_and_survives_restart`

Expected result:

- Revocation requires a new authorized governance transition.
- SQLite restart preserves revoked state.
- Post-restart projection denies with `directive_revoked`.
- Audit chain verification remains true.

### 7. Delegated/derived directives cannot broaden parent authority

Test coverage:

- `test_derived_directive_requires_exact_active_parent_before_authority_use`
- `test_derived_directive_can_only_narrow_parent_scope`
- `test_narrow_derived_directive_activates_and_records_parent_hash`
- `test_delegated_scope_cannot_be_broadened_by_substitution`

Expected result:

- A child must name the exact active parent directive hash.
- A child cannot broaden action, resource, budget, issuer, principal, or time window.
- A valid narrowed child records the parent directive hash in authority evidence.
- Substitution resolves as mismatch/denial, not authority expansion.

### 8. Execution-time reauthorization rejects stale child permits after parent revocation

Test coverage:

- `test_parent_revocation_invalidates_child_and_preissued_child_permit`
- `test_parent_revocation_keeps_child_permit_invalid_after_restart`

Expected result:

- Parent revocation invalidates child projection.
- A preissued child-bound permit cannot be consumed after parent revocation.
- The denial persists across SQLite restart.
- Rejected permit evidence records directive status and parent hash in the existing audit chain.

### 9. Directive state reconciles into existing canonical evidence, not a new ledger

Test coverage:

- `test_directive_components_reject_parallel_state_and_clock_injection`
- directive activation/revocation/permit-binding audit assertions throughout `tests/test_directives.py`

Expected result:

- Directive controller/projection constructors reject parallel state/clock injection by construction.
- Directive activation, revocation, permit binding, permit consumption, and permit rejection record into the existing kernel state/audit path.

### 10. Durable migration preserves parent-bound execution semantics

Test coverage:

- `test_sqlite_existing_permit_directive_table_migrates_parent_hash_column`

Expected result:

- Existing SQLite `permit_directives` tables migrate with nullable `parent_directive_hash`.
- Ordinary non-derived directive bindings remain compatible.
- Parent-bound derived directive semantics are durable after migration.

## Current proof classification

Verified:

- The directive runtime and tests are present on protected `main` at the inspection base.
- The proof covers chat/retrieval non-authority, authenticated activation, exact directive digest binding, untrusted issuer denial, non-broadening derived directives, revocation, restart durability, execution-time parent revalidation, and existing-audit-chain reconciliation.

Recorded:

- PR #116 documented the derived-directive non-broadening proof and its important nonclaim: cross-principal delegated-operator authority remained unproved in V0.
- PR #133 recorded the admitted same-principal derived-directive non-broadening/revocation proof into current state documentation.

Inferred:

- Directive Memory should remain a projection on the existing authority/policy/state/evidence seam rather than a new memory product, new policy engine, or new ledger.

Proposed:

- Future cross-principal delegation should be treated as a separate authority proof with independent issuer/operator identity, scope, expiry, revocation, and execution-time revalidation.

Unknown:

- Production deployment of directive authority with real human signing credentials.
- Cross-principal delegated operator authority.
- Real external-provider containment.
- Cold third-party reproduction.

- semantic memory correctness;
- independent cloud/HSM authority deployment;

## Smallest next proof

The next directive-specific proof should be cross-principal delegation V1 only if it is needed for the next external consequence ceremony. It must prove:

1. authenticated issuer delegates to a distinct operator identity;
2. the operator can only narrow scope;
3. revocation by issuer kills all descendant authority;
4. stale delegated permits fail at execution time and after restart;
5. retrieval/summaries cannot promote the operator's authority;
6. evidence remains in the existing canonical audit chain.

Until then, DM-001 is sufficient for the Pulpo 1.5 claim:

> Memory may help find the rule. Only governance can make the rule authoritative. Execution must re-check the rule before consequence.
