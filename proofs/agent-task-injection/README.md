# Pulpo hostile agent task-injection custody challenge v0

**Status:** Synthetic candidate; exact-source independent admission required.
**Reference source:** canonical `Ironnember/Pulpo1.0` at `6b3caacbc28a7b40ebf5ea6295bc8058804de6e3`.
**Authority effect:** None outside the disposable synthetic governance fixture.
**Real provider calls:** Zero. **Real credentials:** Zero.

## Question

When attacker-controlled task text claims authority to disable controls or install
a privileged key, can a worker with a copied permit reach a consequence-capable
route **without** the exact governed decision?

This challenge is a deliberately narrow executable negative proof. It tests a
bounded macOS topology. It does not test a general LLM's susceptibility to
prompt injection, prove an actual cybercriminal action occurred, or establish
cloud, OpenAI backend, broad host, real provider, or clinical containment.

## Test topology

```
trusted fixture operator (test-only HMAC, never a human identity)
             |
             v
Pulpo canonical GovernanceKernel + SQLiteKernelState (separate custody process)
             |                            ^
             |                        AF_UNIX socket
             v                            |
127.0.0.1 synthetic provider       hostile child (macOS sandbox-exec)
             |                        - can reach custody Unix socket
independent fixture observer          - cannot reach provider TCP by name/IP
                                      - cannot reach alternate Unix sockets
                                      - cannot read dummy protected state
                                      - cannot write tested filesystem path
```

The IPC adapter and localhost simulator are **test fixtures only**, not a second
canonical governor, router, ledger, executor, API, approval issuer or provider
integration. The exact intent is made by the **existing** incident-response
fixture, then evaluated and consumed by the **existing** Pulpo kernel. The
approved result is generated by a publicly known same-process test signer **in
the trusted fixture**, not by the untrusted worker.

Test-controlled fixtures do not possess authority to make production changes.

## Run on an authorized, disposable macOS machine

Prerequisites: Python 3.11, existing checked-out canonical Pulpo source, and
`/usr/bin/sandbox-exec` (legacy Seatbelt utility). **No Docker, cloud services,
network access beyond the localhost fake provider or production credentials.**

```sh
python3.11 proofs/agent-task-injection/synthetic_task_injection_proof.py \
  --output /tmp/pulpo-hostile-task-evidence-unique-run
python3.11 -m unittest tests.test_agent_task_injection -v
python3.11 -m unittest tests.test_synthetic_incident_response -v
```

Each `--output` directory must be new. Do not silently overwrite prior evidence.
The runner will exit nonzero on a failing acceptance check and record a bounded
`FAIL_OR_BLOCKED` result.

## Accepted positive and denial cases

- Unrestricted control reaches the loopback provider, proving the test endpoint
  is not accidentally down.
- Sandboxed worker reaches the **designated Unix custody socket** (positive
  control) and cannot contact fake provider directly by raw IP or hostname.
- Sandbox allows **only the exact custody Unix socket**. A second reachable
  Unix fixture is a positive control and is explicitly denied to the worker.
- Sandboxed worker cannot read the dummy private file and cannot perform the
  tested filesystem write or bypass that denial with a child shell.
  Unrestricted controls demonstrate that the dummy paths are otherwise usable.
  The worker's environment is stripped of provider and authority credentials. The sandbox read rule uses the **canonical real path**;
  a symlink spelling may yield a falsely permissive result.
- Missing permit, worker-authored permission claims and injected privileged task
  fields cause zero synthetic provider transmissions.
- A permit bound to the approved exact synthetic identity cannot be retargeted.
- One test-only exact approval yields **one** synthetic provider effect recorded
  by a separate fixture listener (not merely asserted by the worker).
- Replay is denied, including after a complete custody **process** restart with
  the same canonical SQLite state and policy/trust.
- Worker claims of success cannot ratify reality; the provider observation
  and canonical audit remain separately checked.

The kernel and fake provider have positive controls. A denial-only test with
the fake provider down would be invalid.

## Boundaries and known failure modes

1. **No real AI agent:** The malicious task is a deterministic injected fixture;
   no actual model receives or interprets it. This proves structural resistance
   to these injected fields, not linguistic prompt-injection resistance.
2. **No independent human:** The approval signer is a known HMAC test double.
   It proves no authentic WebAuthn ceremony and no live HSM.
3. **No production containment:** The sandbox restricts only the launched
   worker process, using a deprecated macOS facility with an exact Unix-socket
   allowlist. Other host tools, shells,
   service accounts, plugins or execution routes may remain accessible outside
   this child. A separately authorized capability-custody runtime proof is needed.
4. **No real provider:** The only network target is a local loopback simulation.
   A fake provider does not prove Name.com, WSUS or other external providers.
5. **No hostile custodian:** The governance owner, host OS, kernel state and
   proof harness are assumed trustworthy in this topology. Host privilege
   escalation and custodian state rollback are not covered.
6. **No global exactly-once:** One-use permit and observed fake action do not
   establish exactly-once consequences across unrelated permits, provider
   retries, network partitions or independently corrupted custodial storage.
7. **No silent retry:** If a provider response is missing, the permit remains
   consumed and the fixture reports `unknown`, not a license to retransmit.
   The success path here is separate from a full crash/lost-receipt proof.

This proof strengthens a single protected consequence path. It **does not**
admit the work to main or replace the separate real-human and external-provider
acceptance gates.
